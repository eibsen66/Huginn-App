## Actual chain and ownership

1. `main/huginn_settings_v2.inc:hs2_owner` builds the complete settings document on the existing owner. `xSemaphoreGive(j->done)` publishes completion; two guarded references keep the job/tree alive until owner and handler release it. The handler's reference survives while it serializes/sends.
2. `huginn_settings_v2_handler` uses `cJSON_PrintUnformatted(j->response)`. Its UTF-8 C string is independent allocated storage; `strlen` counts bytes, not Unicode characters. Embedded string NULs are escaped by JSON serialization. It checks the full body against HS2_RESPONSE_MAX=131,072, sets JSON/no-store, and calls `httpd_resp_sendstr`. There is no 20,480-byte branch or settings-field truncation. The live 29,502-byte content was not captured, so its exact values cannot be reconstructed from the phone counters.
3. `esp_http_server/src/httpd_txrx.c:httpd_resp_send` computes Content-Length from the same `strlen` and calls `httpd_send_all` for headers and then body. Settings is **not chunked HTTP**. The buffer remains allocated through the synchronous send; `free(response)` and `hs2_release(j)` occur afterward on success or failure. No buffer-lifetime defect was found.
4. `httpd_send_all` repeatedly calls the session send function, advancing pointer/remaining size for positive partial returns. A negative return immediately becomes ESP_FAIL; `httpd_resp_send` returns ESP_ERR_HTTPD_RESP_SEND. It does not retry negative WANT codes. A zero return makes no progress in this loop, an independent potential stall; it is not evidence for the observed short body and was not pursued as its cause.
5. HTTPS installs `httpd_ssl_send`, which calls `esp_tls_conn_write` and returns its integer unchanged. Negative results post the existing HTTPS error event but are not retried. `esp_mbedtls_write` subdivides the remaining buffer into at most **4,096-byte plaintext writes** in this retained configuration. Normal writes continue until the requested length is consumed. WANT_READ/WANT_WRITE/zero after positive progress return that positive progress; with zero progress they return the raw result. A hard negative after progress returns the negative value, so outer HTTPD does not receive a progress count for that particular call.
6. The handler propagates its send result. `httpd_uri.c` treats a non-ESP_OK handler result as a failed request whose socket should close; HTTPD session processing closes failed sessions and the HTTPS transport cleanup deletes TLS. No successful finalization terminator is needed for a Content-Length body. A failed send can therefore expose HTTP 200 plus the declared length, followed by a short stream. This code path is demonstrated; which lower-level return happened on the phone is unknown.

## Timeouts and the 20,480 boundary

`huginn_https_api_start` inherits the IDF default **five-second send_wait_timeout**; it does not override it. `httpd_main.c` sets SO_SNDTIMEO on the accepted socket. The settings-owner wait is a separate ten seconds before body generation; its failure sends HTTP 504, unlike the measured 200. The app's 20-second abort maps to CANCELLED in its catch path, not this observed diagnostic. No measured target-side send duration is available, so no timeout is asserted as the cause and no timeout is increased.

`mbedtls_net_send` calls the socket write. EPIPE/ECONNRESET map to NET_CONN_RESET; EINTR can map to WANT_WRITE. `net_would_block` tests O_NONBLOCK before treating EAGAIN/EWOULDBLOCK as WANT_WRITE: on a blocking socket a timeout/error can instead map to NET_SEND_FAILED. Consequently **do not equate every WANT_WRITE with a five-second timeout**, and do not claim a specific socket state from the phone result.

20,480 = 5 × 4,096, consistent with five successful outgoing plaintext fragments followed by failure on the sixth. For 29,502 bytes, normal fragmentation is seven full 4,096-byte fragments plus 830 bytes. The working 4,234-byte list needs one full fragment plus 138 bytes. These are configured plaintext boundaries; Fetch chunks need not be one-to-one with TLS records. No SDK rule deliberately stops after five fragments. The size relationship identifies where to observe the failure, not why it occurs.

The working list uses the **same** httpd_resp_send(..., HTTPD_RESP_USE_STRLEN) / HTTPS/TLS chain and frees its encoded JSON only after return. The Settings sendstr wrapper is equivalent to that call, not a separate transport. The list's success proves a smaller transfer works, not that a 29,502-byte send succeeds. The list serializer is bounded independently; the app does not interchange those limits.
